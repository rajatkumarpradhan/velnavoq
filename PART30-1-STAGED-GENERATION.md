# Part 30.1: small, saved generation steps

The UI defaults to staged builds: save the request, generate a short file plan, then one file per separate model call. Each file is a normal immutable proposal. The owner reviews and applies its exact contents through the existing review screen. The next step checks that the applied proposal produced the exact expected source revision and digest. No automatic approval, source apply or deployment is added here. MCP Autopilot remains separate.

Plans contain 1-8 safe static file names, index.html first. A multi-file plan adds a final index.html integration proposal. The first page is standalone, without links to missing assets. Intermediate CSS/JS files are optional until the final page links them. Each step works from saved source, preserves unrelated files, permits only one CREATE/MODIFY, and limits model output to 768 tokens / 3000 characters. The plan response is 160 tokens. Calls have separate 20-second deadlines with no automatic provider retries. A slow provider can still fail even for a small request; staged generation does not guarantee success on the free model or prove a functional booking service.

Sessions persist phase, plan, completed-step count, current proposal, expected source digest/revision and last error. Reload restores the latest session. Retry repeats only the current saved step. Pending review does not advance or call the model. Rejection regenerates that file; approval advances only against the exact source. Unrelated source edits stop with a stale snapshot error. A per-session expiring lock prevents concurrent calls. Sessions are private to the initiating user within their authorized project. Max 20 starts/project/day, instructions capped at 2000 characters; old sessions are pruned on new starts after seven inactive days.

The existing AI engine reserves/settles tokens and records each call, including timeout. Plan reservation is 4000+160 tokens; file reservation is 8000+768 tokens. Missing usage stays conservatively charged. The UI shows charged/reserved tokens and the project cap. Existing service/user/workspace/project token and source storage limits still apply. Starts and next requests also spend existing agent/proposal rate quotas conservatively, including status refresh POSTs. This prevents an unbounded generation loop but can consume request quotas without creating a proposal. The GET refresh does not start work.

UI progress is persisted steps only, never fabricated model percentages. Start stores the session; Generate short plan, Generate next file and Continue after review each send one bounded request. The user can switch to the original single-proposal mode for small changes. Owner review is still required when an editor generated the file.

Deployment: apply migrations/0023_staged_generation.sql before deploying UI/Worker. Preserve production bindings and secrets, ai-adapters.ts and REGISTRATION_ENABLED=true. No paid resources required. This builder does not deploy.

Tests cover the exact clinic request, plan safety, timeout with a mocked slow model and budget settlement, real local D1 proposal persistence, budget display data, pending resume, invalid output retry, cross-user refusal, concurrent lock, file mismatch, quotas, approved sequential advance, rejected retry and unrelated-source refusal. Mobile screenshots are isolated local response fixtures, not production provider proof. Real free-provider success needs a live test after deploy.
